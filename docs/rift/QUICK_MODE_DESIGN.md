# Quick Mode repair design

2026-10-17. Local repair branch; production deployment is not authorised.

The supplied HTML is an interaction reference, not application logic. `/rift/quick` uses `useRift`, `Profile`, `Draft`, `recommend`, `BuildCandidate`, and the same persisted state as the existing detailed routes. No duplicate strategy engine. Compact capture, two five-slot team strips, one candidate, five items plus boots, five runes, two threats, early/next/then purchases, and full analysis. Sheets disclose settings, comparison, item/rune provenance and correction search. Existing manual entry and all detailed routes remain.

Recognition is separate: validated file decode -> content/geometric layout gate -> circle portrait localization -> square-template ranking -> review -> same canonical draft. A screenshot's names, mode, patch and player identity are not inferred. A scoreboard marks postgame context; planning for a future game requires an explicit stage change. Runes after lock-in are informational.

No calibrated auto-accept policy exists with one real scoreboard. All image-derived identities require confirmation, low-confidence candidates remain unknown to rules, manual corrections are protected on subsequent scans. Full screenshots are memory-only; opted-in corrected crops may be retained locally. Supplied private fixtures stay outside public assets and source control. Separate CLI and browser upload tests run the real pipeline; expected labels are read by the evaluator only.

Draft/loading layout validation, representative confidence calibration, Android hardware timing, skin coverage and OCR remain evidence gaps. Local desktop measurements and resized image tests must not be relabelled as phone or held-out performance.

## Implemented control mapping

| Control | Canonical implementation |
| --- | --- |
| Compact defaults sheet | `Profile` and shared `Draft`; `updateState` / `parseState` persistence |
| Scan and review | `scanScreenshot`, `ScanResult`, `applyReviewedScan`; no image in engine |
| Two portrait strips and unknown slots | Same five-element allied/enemy arrays; `setManualSlot` provenance |
| Primary candidate and comparison | Existing `recommend` and `BuildCandidate`; raw utility only in comparison/details |
| Item/rune strips | Patch catalog IDs and acquired local icons; sheet shows full name, mechanics, certainty, source and rationale |
| Threats | `quickThreats` adapts reviewed kit properties and named tactics; unknown kits abstain |
| Early/next/then and detailed ledger | Engine `purchasePlan`, `nextPurchase`, held components/gold/time; no made-up recall minute |
| Copy and Full analysis | Actual selected engine candidate; `/rift/build` reuses the same persisted scenario |

Explicit build choice persists as `Draft.buildChoice` in both Quick and full panels. It is labelled Your choice; Use engine recommendation clears the override. All candidates still recompute from current inputs. Slot badges distinguish S scan, C user edit, and M manual entry.

The small-screen view uses the site's serif/green/paper language and gives Quick its own compact header, scoped only to that route. Champion targets remain at least 44 CSS px high. Long icon labels are abbreviated visibly; full accessible names and sheets preserve exact identities. Sources and diagnostic ledgers stay expandable. The 390×844 supported scenario fits through the purchase path above fixed actions; smaller/retrospective/review states may scroll. No mocked prototype teams/rules were imported.
